# 发布流程与验收清单

本文件定义维护流程，不是已经执行的结果记录。每次发布应另附真实测试日期、环境、结果、失败项与未验证项；不能因为清单存在就视为验收通过。

## 1. 准备版本

1. 确定版本与范围，更新 `Directory.Build.props`、程序集版本、Changelog 和受影响文档。
2. 检查来源、版权和第三方许可材料。发布物不带旧 `LabelTrim.exe`、原 `mutool.exe`、真实面单、临时文件、开发工具和凭据。
3. 确认 README 的运行条件、外部渲染器配置、输出规格与软件一致。
4. 从干净源码树运行构建与测试，记录提交标识、SDK、操作系统及渲染器版本。

```powershell
./scripts/build.ps1 -Configuration Release
./scripts/test.ps1
./scripts/test.ps1 -RendererPath 'C:\Tools\MuPDF\mutool.exe'
```

必须区分核心测试和真实 PDF 集成测试。没有渲染器、桌面环境或打印机时明确记为“未执行”，不能将跳过显示为通过。

## 2. 自动化验证

- [ ] Release 构建无错误、无警告。
- [ ] 核心回归测试通过，尺寸、比例、DPI 与文件保留合同一致。
- [ ] 用本次记录版本的渲染器处理合成单页 PDF，验证输出可以重新打开。
- [ ] 验证多页、空白、损坏/不可读取 PDF、非法裁切及同名输出保护。
- [ ] 验证中文和空格路径、预览后源文件变化、渲染失败与取消清理。
- [ ] 验证通知发生时最终 JPG 已可读取，失败路径不回收原 PDF。

这是一份目标清单。实际自动化覆盖以测试代码和运行结果为准；没有自动化覆盖的项目补充人工记录，不要假称已覆盖。

## 3. 桌面与资源管理器验收

至少记录 Windows 版本、显示缩放比例、文件夹类型、渲染器版本及使用的合成样本。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 原报告的刷新问题 | 先打开本地测试文件夹的 Explorer 窗口，再导入并导出 PDF；全程不按 F5、不点刷新 | JPG 在该已打开窗口中出现，可打开且尺寸正确 |
| 保留原 PDF | 使用默认设置导出 | PDF 和 JPG 都存在，状态正确 |
| 回收 PDF | 仅在测试目录，勾选回收后导出 | JPG 已验证后才尝试回收；成功时可在回收站恢复 |
| 回收不可用 | 用不支持回收的位置或受控失败条件 | JPG 保留，PDF 保留，给出警告 |
| 重名 | 预先放入同名 JPG 后导出 | 不覆盖已有 JPG，原 PDF 保留 |
| 交互裁切 | 拖动四角、移动到边缘、连续旋转与重新检测 | 无越界、无异常；预览与导出布局一致 |
| 异步切换 | 快速切换文件、移除和清空队列 | 旧预览不覆盖新选择，资源正确释放 |
| 停止和关闭 | 渲染或批处理中停止/关闭 | 后续任务停止；没有损坏的最终输出或误回收 |
| DPI 与窗口布局 | 在目标支持的缩放比例检查窗口、按钮、队列、提示 | 控件可见可操作；记录实际检查过的比例 |

资源管理器回归要验证已经打开的窗口，不能只靠重新打开目录或截图证明自动刷新。网络共享、移动盘和同步目录应单独记录结果；本地固定磁盘成功不代表这些位置也通过。

## 4. 打印验收

- [ ] 输出 1600×2400、400 DPI，内容未被拉伸。
- [ ] 检查姓名/地址区域和完整条码均未被裁掉。
- [ ] 确认所用纸张是实际的 4×6 英寸还是 100×150 mm，并检查打印驱动缩放。
- [ ] 打印并扫描至少一张合成测试条码，记录打印机与扫描器；没有设备则记录未验证。

## 5. 打包与复核

```powershell
./scripts/package.ps1 -Version 2.2.0
```

生成 `artifacts/ParcelCrop-4x6-2.2.0-win-x64.zip` 和 SHA-256 校验文件。解压到新的含空格路径，从解压后的包实际启动，并按照用户指南配置外部渲染器。检查包内包含应用、所需配置、许可与使用说明，且不含外部渲染器或私人文件。

GitHub Release 应提供便携包、校验文件、对应源码标签和发行说明。发行说明应写清：外部 MuPDF 必须单独配置、默认保留 PDF、恢复源码基线、已验证环境、未验证项以及已知限制。校验值应从实际上传的最终文件重新计算，不从旧文件复制。

## 6. GitHub 发布

1. 将准备好的源码提交到目标公开仓库，确认文档相对链接有效。
2. 检查 CI 的实际结果；不要使用未经运行的“通过”徽章或状态描述。
3. 审查最终差异和打包内容，创建对应版本标签（例如 `v2.2.0`）。
4. 创建 Release，上传已复核的 ZIP 和校验文件，链接该标签的源码。
5. 从 GitHub 实际下载资产，核对哈希和首次运行步骤，然后记录发布时间与下载链接。

仓库创建、源码推送、标签和 Release 是不同步骤；如其中某步受身份验证或权限阻止，应准确说明完成到哪一步，不宣称“已发布”。未来修复使用新版本，不悄悄替换已发布资产。
